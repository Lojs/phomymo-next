10 of 15 closed with code

Details of the ones fixed during the v1.0.16/17/18 cycle (F1, F2, F6, F9 were
already fixed in v1.0.16 itself):

F1  paperWidthMm() was printing a byte count with an "mm" suffix. That is only
    correct at 203 DPI; at 300 DPI an M02 Pro read "78mm" when the paper is
    53 mm. Now converts through the printer's own DPI. [VERIFIED]

F2  warnIfWiderThanPrinter() runs once per label, so a batch queued one toast
    per record. A latch now guards it, reset by beginPrintJob() at the start of
    printCurrent, printDensityTest and runBatch. [VERIFIED]

F6  A failed GATT setup fired the disconnect handler during connect, leaving the
    UI in a torn-down state. The handler is now detached and a generation
    counter bumped before gatt.disconnect(). [VERIFIED]

F9  race() attached an abort listener per delay op and never removed it; 200
    delay operations left 200 listeners on the signal. Now 200 -> 0. [VERIFIED]

N1  The README claimed "Neither Safari nor Chrome on macOS implements Web
    Bluetooth or WebUSB". Chrome and Edge on macOS do implement both, and the
    app gates on feature detection alone (`'bluetooth' in navigator`), so the
    documentation contradicted the code. Rewritten, and a test now reads
    printing.ts to fail if a platform sniff ever appears. [VERIFIED]

N2  describe() returned "M-series (72)" for an unrecognised printer — the
    millimetre conversion was computed but the unit was discarded. [VERIFIED]

N3  Two separate mm conversions existed and had drifted. A 53 mm label on a
    52.8 mm head warned that the printer prints 53 mm — the very width the
    warning exists to report as clipped. One exported widthBytesToMm() now
    serves both the comparison and the displayed number, formatted to one
    decimal. [VERIFIED]

F8  waitForDialogToClose() resolved on its 60-second timeout exactly as if the
    user had answered the model picker, so the print went out on printerModel
    'auto' — a guessed dpi and encoding for a machine nobody identified. The
    timeout now means "not configured": the connection is abandoned, the
    transport is torn down, connectPrinter returns false, and a new translated
    message tells the user to pick a model. [VERIFIED — test fails on the
    previous code, confirmed by stashing the fix]

F7  `expect` was plumbed through Op, Transport and BLETransport.waitForResponse
    to filter which printer frame satisfies a wait. No caller ever passed one,
    so the P12 handshake problem its own comment described was never actually
    solved. Removed rather than left as a dead path into a waiter; the reason is
    kept in the comments so a filter that returns comes back with a caller.
    [VERIFIED]

N4  Four separate gaps, all now closed:
      - Single-byte protocol fields (density, heat settings, line spacing) took
        raw values: a NaN became 0 in the Uint8Array and a value past 255
        wrapped round. All go through clampByte(). Golden tests confirm valid
        output is byte-for-byte unchanged.
      - multiLayout() clamped the zone count but not labelWidth / labelHeight /
        gapMm, so a NaN produced NaN geometry that passed every later check.
      - The PNG/PDF export path (scale 4) had no canvas guard, unlike printing.
      - Image, PDF, CSV and design imports had no size limit. Now 25 MB, with
        the limit named in the error.
    [VERIFIED — 6 tests fail on the previous code]

N5  The release gate interpolated ${{ github.ref_name }} directly into run:,
    which GitHub recommends against. Now passed through env:. Low risk (pushing
    a tag needs write access) but this is exactly where a mistake is cheapest.
    [VERIFIED]

2 of 15 closed by evidence

These were the review's largest open items, and both were settled by measuring
the actual printer rather than by changing code. The user's Phomemo was checked
three ways:

  1. Windows PowerShell (Get-PnpDevice) reported it as:
         USB Printing Support   USB\VID_0483&PID_5740\1234567890ABCDEF
     Windows binds a device to this class only when it exposes a printer-class
     interface — a device reporting class 255, 10 or 2 appears under a different
     name entirely.

  2. chrome://usb-internals confirmed the identity:
         Jieli Technology — VID 0x0483, PID 0x5740

  3. The Inspect panel confirmed the decisive fact:
         Interface 0: Printer (Class Code: 7), bulk IN + bulk OUT

Consequences:
  F4  usb.ts searches for interfaceClass === 7 and throws
      "No printer-class interface found" otherwise. The printer reports exactly
      7, so the path is correct. usb.ts is unchanged since v1.0.12. [PLATFORM]

  F5  USB_DEVICE_FILTERS' first entry is { vendorId: 0x0483, productId: 0x5740 }.
      The printer matches it exactly, so auto-reconnect works for it. [PLATFORM]

Both findings remain valid as generic statements about other hardware, and both
are now documented as such rather than silently closed.

2. WHAT THE HARDWARE INVESTIGATION FOUND (not in the review)
================================================================================

The user reported a persistent "Permission denied" error when connecting over
USB. It is not an application bug. Root cause, established on their machine:

  Windows binds the printer to a kernel-mode print driver, which is why Device
  Manager shows it as "USB Printing Support". Once Windows has claimed the
  interface, no browser can claim it — WebUSB on Windows works through WinUSB,
  which requires the device to be free of a system driver binding.

Supporting evidence, all consistent with that single cause:
  - "Permission denied" toast                          (app's normal mapping of
                                                      navigator.usb.requestDevice()
                                                      throwing SecurityError)
  - Transfer Errors on device/configuration/string    (the Inspect page reading
    descriptor fetches in the web page
  - window.isSecureContext === true                    (HTTPS is correct, so the
                                                      secure-context theory is
                                                      excluded)

Resolution, by platform:
  Windows + Bluetooth   WORKS. BLE does not pass through the USB driver binding.
  Linux / Raspberry Pi + USB   WORKS. No print driver binds the device, so
                               WebUSB works normally.
  Windows + USB         Requires a manual WinUSB driver override from an
                        administrator. Documented, multi-step, and it can break
                        normal Windows printing. Not recommended.

No application change is warranted. The app's own USB code is correct.

3. PROJECT STATUS — IS IT SOUND AND STABLE?
================================================================================

Short answer: YES, with one honest caveat.

--------------------------------------------------------------------------------
3.1  WHAT IS GENUINELY STRONG
--------------------------------------------------------------------------------

  - Every fix is pinned by a test that FAILS on the previous code. This was
    verified for each batch by stashing the fix and re-running, not assumed:
    6 failures for N4, 2 for F8, 6 for N1-N3, 9 for the v1.0.18 batch.

  - 1275 tests across 55 files, all passing. Coverage is above every configured
    gate with margin, and the margin is growing, not eroding
    (80.63% -> 80.66% -> 80.75% statements across three releases).

  - Golden tests compare protocol output byte-for-byte against a frozen copy of
    the original implementation. This is what let the encoder clamping be proven
    safe: valid output is provably identical.

  - The release pipeline is genuinely gated. The image is published only if the
    verify job passes, pull requests are never published, and a tag whose number
    disagrees with package.json is rejected before anything ships. The CI run for
    v1.0.18 succeeded on both main and the tag.

  - Test counts in the README are read off the real run, not estimated, and a
    tag gate prevents the UI from ever misreporting its own version.

  - There is no server-side state, no accounts, no telemetry, and the raster is
    generated in the browser and never leaves the device. The attack surface is
    genuinely small.

--------------------------------------------------------------------------------
3.2  THE CAVEAT — WHAT IS STILL WEAKER THAN THE REST
--------------------------------------------------------------------------------

The `any` in BLETransport. This is the one place where the code is knowingly
less safe than a reviewer might assume, and it was left that way deliberately.

  Web Bluetooth and WebUSB types are now installed (@types/web-bluetooth,
  @types/w3c-web-usb) and wired into tsconfig's `types` allowlist, so
  navigator.bluetooth, navigator.usb and every requestDevice option are type
  checked. That shim previously declared both as `any`, meaning a misspelled
  property compiled fine and failed at the printer.

  The five handles inside BLETransport — device, server, service, writeChar,
  notifyChar — remain `any`. This was attempted and reverted. Naming the spec
  types surfaced roughly twenty errors, most of them genuine `possibly null`
  (the transport nulls these on disconnect) plus a few out-of-spec properties
  the transport bolts onto the device for its own bookkeeping
  (_hasDisconnectHandler). The only way through was non-null assertions, which
  would silence the compiler without making the printer path any safer.

  Decision: left as `any`, with a comment that states the reason honestly
  instead of claiming the types were unavailable. This is recorded as known
  remaining technical debt, not presented as fixed.

  Realistic risk: LOW. These values come from the browser's own Web Bluetooth
  implementation, not from user input, and the code paths they feed are covered
  by tests that exercise disconnect, failure and cancellation.
  Worth doing: yes, but as its own piece of work with a printer or a device
  simulator available — not folded into a maintenance release.

================================================================================
5. KNOWN, DELIBERATELY DEFERRED
================================================================================

5.1  NO IMAGE SCAN, SBOM OR PROVENANCE ATTESTATION
    The published container image is not scanned for vulnerabilities and carries
    no SBOM or provenance. Not done because it needs a decision about tooling
    and where scan results are allowed to fail the build — that is a policy
    choice, not a code change, and a wrong default either blocks releases or
    reports are ignored. Recommended as the next deliberate piece of work.

5.2  `any` ON THE FIVE BLUETRANSPORT HANDLES
    Detailed in section 3.2. Deliberate, documented, low risk.

5.3  NO REAL-HARDWARE TESTING
    Every fix in this report was verified by reading code and running tests. None
    was verified by printing a label. The one item that genuinely needs it is
    5.2, and the F4/F5 conclusions were reached by measuring the hardware rather
    than by assuming.

The project is sound and stable as of v1.0.18.

  - All 15 findings from the v1.0.16 review are resolved: 13 with code, 2

  2. Typing the BLETransport handles, with hardware or a simulator available (3.2)
  3. Periodic re-review now that the review cycle has produced this much value
